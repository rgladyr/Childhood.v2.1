# C# Code Style — процесс работы

Полный регламент правил — `docs/code-style.md` (§1-§13).
Этот скилл задаёт **как работать**, а не **какие правила**.
Перед сложной правкой открой соответствующий параграф `code-style.md`
и прочитай — не полагайся на память для правил §2 (составное выражение),
§11 (параметры) и §2 (throw/new): они контринтуитивны.

---

## Когда активируется

Любая работа с `.cs` файлами:
- Написание нового кода
- Редактирование существующего
- Code review
- Рефакторинг под стиль
- Обсуждение архитектуры с примерами кода

Применяется ко всему выходному C#-коду без исключений, даже если
пользователь не просил «соблюди стиль».

---

## Процесс работы

### Шаг 1. Подготовка

Перед началом правки:

1. Если задача больше одного файла — составь план: список файлов ×
   список параграфов code-style.md, которые будут затронуты.
   Покажи план пользователю, дождись подтверждения.
2. Открой `docs/code-style.md` и прочитай параграфы, релевантные
   задаче. Особенно если затронуты §2 (переносы), §11 (параметры),
   §6 (порядок методов).
3. Если правил много, лучше дробить задачу: «пройдись только по §11 во всём
   файле, потом отдельной итерацией по §2». Не пытайся применить все 13
   параграфов одним проходом — фокус размывается.

### Шаг 2. Правка

Применяй файл за файлом. Внутри файла — итерация по правилам.

**После каждой правки `.cs` файла** (после каждого Edit/Write,
не «в конце задачи»):

```bash
dotnet format --include <относительный-путь-к-файлу>
dotnet build --nologo -v q
```

Если `dotnet format` изменил файл → ты нарушил правило, выраженное в
`.editorconfig`. Прочитай diff, запомни какое правило нарушил,
не повторяй в следующих правках того же типа.

Если `dotnet build` показал error/warning — исправь до перехода
к следующему файлу.

### Шаг 3. Механическая проверка §11 — ОБЯЗАТЕЛЬНО

Это самое часто нарушаемое правило. Простая текстовая проверка
перед самопроверкой по чеклисту:

```bash
# Для каждого изменённого .cs файла
grep -nE '=\s*[A-Za-z_][A-Za-z0-9_.<>]*\(.+,.+\)' <file>
```

Эта команда находит **все** строки вида `... = SomeName(arg1, arg2, ...)`
на одной строке — все они нарушения §11, без исключений. Длина строки,
короткое имя метода, литералы, self-assignment — не имеют значения.

Каждую найденную строку нужно переписать в многострочную форму:

```csharp
// БЫЛО (найдено grep'ом):
this.ThrottleInput = Mathf.Clamp(this.ThrottleInput, -1, 1);

// СТАЛО:
this.ThrottleInput =
    Mathf.Clamp(
        this.ThrottleInput,
        -1,
        1);
```

После всех правок повтори grep — должен вернуть пустой результат.

Если в проекте нет `grep` (Windows без unix-tools) — пройдись по diff
вручную и ищи паттерн глазами: `= ИМЯ(.., ..)` или `= ТИП.ИМЯ(.., ..)`
или `= new ТИП(.., ..)`.

### Шаг 4. Самопроверка по чеклисту

Перед тем как сказать «готово» по файлу, **подсчитай**
(не «проверь, что нет нарушений», а именно посчитай):

1. **Все вызовы вида `= Foo(a, b)` на одной строке (§11).**
   После grep из Шага 3 должно быть 0. Особое внимание на:
   - Self-assignment: `x = Foo(x, ...)`, `this.X = Foo(this.X, ...)`.
   - Литералы как аргументы: `new Color(1f, 0f, 0f)`, `Mathf.Clamp(v, -1, 1)`.
   - Свойства слева: `this.Position = Vector3.Lerp(a, b, t)`.
   - Короткие API: `Vector3.Cross`, `Math.Min`, `Path.Combine`,
     `Mathf.Clamp`, `Mathf.Lerp`, `HashCode.Combine`, `string.Equals`,
     `new Vector3(...)`, `new Color(...)`, `new Bounds(...)`.
2. **Объявления методов с 2+ параметрами на одной строке (§11).**
   Должно быть 0.
3. **Составное выражение на одной строке (§2).** Сколько присваиваний
   с ≥2 операндами и операторами на одной строке? Должно быть 0.
4. **this. (§9).** Сколько обращений к членам класса без `this.`?
   Должно быть 0.
5. **if без скобок (§10).** Должно быть 0.
6. **Атрибуты в одних `[]` через запятую (§8).** Должно быть 0.
7. **Сокращения в именах (§3).** Сколько `res`, `usr`, `msg`, `data`
   и подобных? Должно быть 0.
8. **string == / .Equals() (§13).** Сколько случаев сравнения строк
   не через `string.Equals(..., StringComparison.OrdinalIgnoreCase)`?
   Должно быть 0.

Если хоть один пункт > 0 — исправь и пройди чеклист заново.

### Шаг 5. Финальная проверка

Перед сообщением пользователю «задача выполнена»:

```bash
dotnet format --verify-no-changes
dotnet build --nologo
dotnet test --nologo
```

Все три должны быть зелёными.

## Особое внимание: §11 и его ловушки

Это правило нарушается чаще всех остальных вместе взятых. Все нарушения
сводятся к **четырём паттернам, которые нужно научиться распознавать**.

### Паттерн 1. Короткий вызов «и так читается»

Соблазн: вызов помещается на 80 символов и читается легко, зачем дробить.
Правило: дроби. Длина не критерий.

```csharp
// ЗАПРЕЩЕНО
var flatRight = Vector3.Cross(Vector3.up, flatForward);

// ПРАВИЛЬНО
var flatRight =
    Vector3.Cross(
        Vector3.up,
        flatForward);
```

### Паттерн 2. Self-assignment (`x = Foo(x, ...)`)

Соблазн: «это же просто обновление переменной/свойства, а не вычисление».
Правило: это всё ещё вызов с 2+ аргументами. Дроби.

```csharp
// ЗАПРЕЩЕНО
this.ThrottleInput = Mathf.Clamp(this.ThrottleInput, -1, 1);
position.x = Mathf.Lerp(position.x, target.x, dt);

// ПРАВИЛЬНО
this.ThrottleInput =
    Mathf.Clamp(
        this.ThrottleInput,
        -1,
        1);

position.x =
    Mathf.Lerp(
        position.x,
        target.x,
        dt);
```

### Паттерн 3. Литералы как аргументы

Соблазн: `new Color(1f, 0f, 0f)` — три литерала, выглядит как «инициализация».
Правило: три аргумента. Дроби.

```csharp
// ЗАПРЕЩЕНО
var color = new Color(1f, 0f, 0f);
var bounds = new Bounds(Vector3.zero, Vector3.one);

// ПРАВИЛЬНО
var color =
    new Color(
        1f,
        0f,
        0f);

var bounds =
    new Bounds(
        Vector3.zero,
        Vector3.one);
```

### Паттерн 4. Свойство слева

Соблазн: «это присваивание свойства, а не локальной переменной, для них
правило другое». Правило: правило одинаковое. Дроби.

```csharp
// ЗАПРЕЩЕНО
this.Position = Vector3.Lerp(start, end, t);
this.Velocity = Vector3.ClampMagnitude(velocity, maxSpeed);

// ПРАВИЛЬНО
this.Position =
    Vector3.Lerp(
        start,
        end,
        t);

this.Velocity =
    Vector3.ClampMagnitude(
        velocity,
        maxSpeed);
```

### Универсальная проверка

Если в строке есть символ `=` (не `==`, не `=>`), и справа от него —
вызов вида `ИМЯ(...)` с **2+ аргументами через запятую**, это нарушение.
Точка. Не ищи поводов оставить как есть.

Единственное исключение — **1 аргумент**:

```csharp
// 1 аргумент — одна строка, без переносов
var hash = Animator.StringToHash("Roll");
var token = await this.LoadTokenAsync();
this.IsActive = this.Validate(token);
```

## Особое внимание: §2 — составное выражение

Если справа от `=` 2+ операндов с операторами:
- `=` остаётся на первой строке
- Операнды — каждый со своей строки
- Оператор **перед** операндом, не после

```csharp
// ПРАВИЛЬНО
this.PitchInput =
   -this.PitchAngle
  * this.autoPitchLevel;

// ЗАПРЕЩЕНО
this.PitchInput = -this.PitchAngle * this.autoPitchLevel;
```

## Особое внимание: §2 — throw/new

`new` на следующей строке, выровнен по `w` от `throw`.

```csharp
throw
  new InvalidOperationException("Сообщение.");
```

## Жёсткие запреты

- НЕ удалять методы расширения и инфраструктурные классы со ссылкой
  на «нет использований» — может использоваться через DI/рефлексию (§1).
- НЕ объединять рефакторинг стиля и изменение бизнес-логики в один коммит.
- НЕ применять массовый regex/sed-replace по всему репозиторию без
  поштучной проверки — §2 и §11 имеют исключения, которые сломаются.
- НЕ переходить к следующему файлу, пока в текущем `dotnet build`
  падает с ошибками стиля.
- НЕ говорить «готово», пока не прошёл финальный пайплайн (Шаг 5).
- НЕ гадать по правилам §2/§11 — открой code-style.md и прочитай.
- НЕ оставлять `= Foo(a, b)` на одной строке ни при каких обстоятельствах:
  ни на коротких вызовах, ни на self-assignment, ни на литералах,
  ни на свойствах. Длина не критерий, контекст не критерий.
- НЕ пропускать grep-проверку из Шага 3.

## При сомнении

Правило неоднозначно или конфликтует с другим? Остановись, процитируй
оба правила пользователю, спроси трактовку. Один уточняющий вопрос
лучше десяти итераций исправлений.
